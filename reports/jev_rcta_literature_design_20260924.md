# JEV-RCTA：四个改造方向的顶会文献与架构建议

日期：2026-09-24。范围：文献研究、现有代码对照与设计建议；本次没有调用 JEV、运行新实验或修改推理实现。下文“迁移设计”均为待验证方案，不代表原论文已经验证 JEV 或 LongRCA。

## 1. 对上一版的修正

当前 `scripts/jev_rcta.py` 已经使用 Choice，也在单道题内读取选项概率，但 segment 召回后的保留数量、候选缩减和追溯深度仍主要由固定配置决定。上游关系标签尚未形成完整的自适应问答控制器；证据卡主要保存截取的原文，而不是一套可检索、可核验的语义标签。

因此，“更多次选择题”不足以构成下一版。应让选择结果的完整分布决定保留哪些假设、补充哪些原文、下一步问什么，以及何时停止。

## 2. 精选论文与可借鉴的方法

以下八篇均已核对论文原文或正式论文集；会议、年份不是仅根据预印本上传日期推断。

| 方向 | 论文与会议 | 原论文方法 | 我们可以迁移的部分 | 不能直接继承的结论 |
|---|---|---|---|---|
| segment 自适应选择 | **Classification with Valid and Adaptive Coverage**，Romano、Sesia、Candès，NeurIPS 2020，[论文](https://proceedings.neurips.cc/paper/2020/file/244edd7e85dc81602b7615cd705545f5-Paper.pdf) | 结合分类概率排序与校准样本，构造大小自适应的预测集合。 | 清晰的选择保留较少候选，模糊的选择保留更多候选；把固定 top-k 改成有校准依据的集合选择。 | 原文覆盖率依赖相应假设和校准程序；不能把若干节点的局部覆盖率直接当成整棵搜索树的覆盖率。 |
| 概率使用的前提 | **On Calibration of Modern Neural Networks**，Guo 等，ICML 2017，[论文](https://proceedings.mlr.press/v70/guo17a.html) | 研究预测概率与实际正确率的不一致，讨论温度缩放等后处理校准。 | 分题型检查 JEV 分数的可靠性，再确定跳过、保留与停止阈值。 | 该论文没有研究 JEV；不能据此直接断言 JEV 已校准或未校准。 |
| 标签代替自由摘要 | **Concept Bottleneck Models**，Koh 等，ICML 2020，[论文](https://proceedings.mlr.press/v119/koh20a.html) | 先预测人类可理解的概念，再通过概念预测目标；可以修改概念检查下游影响。 | 将轨迹变成事件类型、错误现象、依赖、修复状态等因子化标签，形成可检查的中间表示。 | 原文使用概念监督训练；调用现成模型打标签不等同于复现 CBM，更不自动获得因果解释。 |
| 标签参与控制 | **Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection**，Asai 等，ICLR 2024，[论文](https://proceedings.iclr.cc/paper_files/paper/2024/file/25f7be9694d7b32d5cc670927b8091e1-Paper-Conference.pdf) | 使用检索与评议标记判断检索需求、相关性、支持程度及输出效用。 | 用 Choice 标签触发补证、验证、继续搜索等动作，让标签影响流程。 | 原文训练了生成与评议能力；它不是“零训练标签全面替代摘要”的证据。 |
| 自适应问题选择 | **Near-Optimal Bayesian Active Learning with Noisy Observations**，Golovin、Krause、Ray，NeurIPS 2010，[论文](https://proceedings.neurips.cc/paper/2010/file/1e6e0a04d20f50967c64dac2d639a577-Paper.pdf) | EC² 在有噪声、不同成本的测试中，选择能有效区分不同假设类别的测试。 | 把根因候选看作假设，把每道 Choice 看作付费且可能出错的测试，优先提出能区分竞争解释的问题。 | 其理论保证需要概率模型等条件；用启发式问题排序不能声称已经实现 EC² 的最优性保证。 |
| 树搜索与回溯 | **Tree of Thoughts: Deliberate Problem Solving with Large Language Models**，Yao 等，NeurIPS 2023，[论文](https://papers.nips.cc/paper/2023/hash/271db9922b8d1f4dd7aaef84ed5ac703-Abstract-Conference.html) | 显式组织中间状态，生成和评价分支，通过搜索探索、前瞻和回溯。 | 保存多个根因分支，遇到反证时回退；分支宽度由概率与预算控制。 | 原文以文本 thoughts 为主要状态；我们使用标签、候选和原文指针，是另一种状态设计。 |
| 问题模块化 | **Decomposed Prompting: A Modular Approach for Solving Complex Tasks**，Khot 等，ICLR 2023，[论文](https://arxiv.org/pdf/2210.02406) | 将复杂任务分解给专门的子任务处理器，可递归调用，也可接入符号函数。 | 建立“找约束、找执行、查依赖、查修复、判责任”等小问题模块，每个模块独立定义输入、选项与证据需求。 | 原文含生成式分解器；我们的初版可以由程序选择模板，不能把两者视作同一实现。 |
| 多轮补证 | **Interleaving Retrieval with Chain-of-Thought Reasoning for Knowledge-Intensive Multi-Step Questions**，Trivedi 等，ACL 2023，[论文](https://aclanthology.org/2023.acl-long.557/) | IRCoT 将检索与推理交替进行，当前推理决定后续检索内容。 | 已选标签与候选决定下一轮检索哪些原文，取回原文后再问下一道 Choice。 | 原文生成自然语言推理；这里以结构化状态驱动检索，效果需要另行评估。 |

建议精读顺序：**EC² → 自适应预测集合 → Concept Bottleneck Models → Decomposed Prompting → Self-RAG / IRCoT**。Tree of Thoughts 主要用于借鉴搜索和回溯，不足以单独解决问题设计。

## 3. 方向一：用 Choice 分布选择 segment 和细化粒度

### 3.1 先区分三个量

TypeSafe 官方说明：`probabilities` 是所有选项的分布；`confidence` 是根据该分布形状计算的集中程度指标。它不是厂商承诺的任务正确率。官方也建议针对具体应用验证阈值。[Confidence 文档](https://docs.typesafe.ai/confidence)

本方案分别考虑：

1. **可疑程度**：该 segment 包含当前失败相关证据的支持程度。
2. **不确定性**：在给定问题和选项下，模型是否难以区分答案。
3. **补证价值**：继续读取这个 segment 是否可能改变最终根因判断。

高置信地选择“无关”与高置信地选择“存在错误”应触发不同动作；低置信也不意味着值得无限追问。

### 3.2 segment 选择与 segment 内选择分开处理

- **跨 segment**：先以相同定义的小问题获得标签和分数，建立整个轨迹的粗粒度索引。对分数做分题型校准后，决定哪些段进入精读、哪些暂缓、哪些需要补足上下文。不能将不同选项集合下的原始最大概率直接比较。
- **segment 内**：对互斥的候选步骤使用自适应候选集合。分布集中时减少保留数量；分布分散时扩大保留范围，必要时继续划分 segment。
- **分段粒度**：按消息、工具调用—返回、交接和产物边界建立层级；字节上限作为接口约束。支持段→步骤→原文片段的逐级展开，并能跨边界取上下文。
- **召回补救**：保留“候选之外”“证据不足”等出口，能重新打开暂缓的 segment。某段只有传播或修复证据，也可能对另一段的根因判断有用。

一个直观示例：假设同一道题的四个选项分布为 `[0.86, 0.08, 0.04, 0.02]`，另一道为 `[0.30, 0.27, 0.23, 0.20]`。采用示意性的累计质量 0.90 规则，前者保留两个、后者保留四个。这个例子仅说明动态数量，**不是严格 APS 实现，也不代表 90% 正确率或覆盖率**。

若要报告 conformal coverage，必须按论文实现相应分数、校准和集合构造，并评估实际使用的整套选择流程。按完整轨迹划分校准集与评估集，避免同一轨迹的相关 segment 被随机分到两侧；自适应搜索后也不能直接继承静态节点的保证。

## 4. 方向二：标签作为索引，原文作为证据

建议采用因子化标签，不把所有属性拼成一个超大分类问题。

| 字段 | 示例值 | 用途 |
|---|---|---|
| 事件类型 | 指令、计划、执行、工具结果、检查、修复、结论、其他 | 寻找合适的证据位置 |
| 局部现象 | 约束冲突、执行失败、状态不一致、结论缺支持、未见异常、不足以判断 | 建立竞争解释 |
| 与当前假设关系 | 支持、反驳、无关、证据不足 | 更新分支和选择反证问题 |
| 依赖状态 | 有明确来源、来源有多个候选、未找到来源 | 决定是否追溯及追溯哪些步骤 |
| 修复状态 | 有成功修复证据、错误仍持续、修复结果未知 | 区分早期错误和最终有效根因 |
| 原文位置 | trajectory ID、step ID、片段边界、原文哈希 | 回到可核查的原始记录 |

这些是拟议标签，不是已有人工真值。保存每个字段的完整分布；文件名、步骤编号、原文偏移等能够从日志确定的信息由程序提取，不让模型编造。

标签不能完全承担根因判断：罕见错误可能超出标签体系，错误标签也会传播。每张卡保留原文指针，需要验证时取回完整相关片段；最终输出关联证据位置。标签承担筛选和调度，最终判断仍需阅读证据。

## 5. 方向三：有噪声、可回溯的问答搜索

树节点保存：候选根因、已有问题及完整回答分布、标签、已读取的证据位置、待核查分歧、剩余预算。树边是一次问题或取证动作。

真正需要决定的是“什么问题最能区分目前的竞争解释”。例如：

- H1：上游指令错误，执行者照做。
- H2：指令正确，执行者偏离。
- H3：局部执行正确，最终总结错读结果。

此时“原始指令是否包含同一错误要求”可能比“这个步骤是否可疑”更有价值，因为前者直接区分 H1 与 H2。

EC² 的具体借鉴是：考虑测试结果能消除多少不同假设类别之间的混淆，再结合测试成本。原论文还指出，噪声下简单贪心信息增益可能很差，因此不应把“最大熵问题”直接称为最优策略。

可实现的初版先用开发集估计各问题模块的判别能力、错误率与成本，按“预计减少竞争解释的程度 / 预计新增 token 成本”排序。这是工程近似，不是已具备理论保证的 EC²。若缺少足够估计数据，先用明确的规则优先核查候选之间存在分歧的事实。

同时保留以下机制：

- 低置信时保留多个分支，优先补原文，避免一次判断就永久删除其他解释。
- 新证据反驳当前分支时回溯；可重新打开之前暂缓的 segment。
- 不把重复阅读同一证据得到的多个回答当成独立证据相乘。
- 满足预定证据检查且候选足够稳定时停止；预算耗尽仍无法区分时报告不确定性。

TypeSafe 官方已有基于 Choice 概率的层级分类与 beam search 示例，可作接口实现参考。该示例保留固定 K 条路径；我们拟议的动态分支数与取证动作还需要自己设计和验证。[官方示例](https://docs.typesafe.ai/cookbooks/hierarchical_classification)

## 6. 方向四：问题树与证据树联动

要同时维护两种结构：

- **证据层级**：轨迹→事件段→步骤→具体原文片段。
- **问题依赖**：失败现象→竞争解释→需要什么证据→证据核验→传播或修复→责任归属。

问题依赖不必固定成每条样本都走完的同一棵树。一次回答决定下一步进入哪个模块，模块再决定取哪部分原文。下面是示意分支，不是实验结果：

| 当前分歧 | 本轮 Choice 问题 | 选项示例 | 对应动作 |
|---|---|---|---|
| 不清楚失败表现 | 最终可观察到的失败主要是哪一类？ | 约束未满足／执行失败／错误结论／其他／证据不足 | 定位相应约束、工具结果或最终结论 |
| 指令错误还是执行偏离 | 哪种记录最能补足当前判断？ | 原始任务约束／上游交接／实际调用参数／后续验证／尚不能确定 | 程序检索相应记录 |
| 多处原文可能相关 | 哪个片段直接说明待核查的要求？ | 原文片段 A／B／C／以上都不是／不足以判断 | 记录被选中的真实片段 ID |
| 上游与本地责任不清 | 原始指令是否明确要求了争议行为？ | 明确要求／明确不允许／没有规定／证据不足 | 分别继续核查上游要求、执行偏离或缺失证据 |
| 早期错误是否仍有效 | 最终提交前是否已有成功修复的直接证据？ | 已验证修复／已验证仍存在／结果未知 | 读取后续修复与验证记录；必要时回溯 |
| 有多个责任主体 | 哪个角色作出了引入该错误的决定？ | 本轨迹中的实际角色／其他来源／证据不足 | 联合核对决策与执行记录 |

每个问题只检验一个清楚的事实。加入“证据不足”和“以上都不是”，但区分二者：前者表示无法判断，后者表示给定选项被现有证据排除。避免先暗示某个角色有错，再让模型寻找支持它的片段；每个候选都应有反证检查。

证据由程序从原始轨迹取回。JEV 选择的是既存片段及其关系，不把它生成的说明当成新的事实。角色判断也不强行等同于错误步骤的发言者。

同一个 TypeSafe 请求中的多个问题独立读取同一 state，不会自动看见彼此的答案。因此，真正有先后依赖的问答需要分轮调用；只有相互独立的标签字段适合放在同一轮。[Choice 文档](https://docs.typesafe.ai/primitives/choice)

## 7. 整合后的架构与验证顺序

拟议流程：**原始轨迹与可回溯索引 → 粗粒度标签 → 自适应候选集合 → 选择最有判别力的问题 → 取回相关原文 → 更新标签和候选 → 验证根因与责任角色**。中间允许补证、扩大集合和回溯。

优先实施顺序：

1. 审计 Choice 回包结构与概率语义，按题型评估可靠性；把固定候选截断改为可校准的自适应保留规则。
2. 引入标签与原文指针，保留相同取证预算，对比现有证据卡。
3. 建立少量清晰的问题模块，先验证问答依赖与每个模块的局部正确率。
4. 引入成本感知的问题选择、动态分支与回溯，再比较完整系统。

未来实验至少区分四个增量，不能一次全部更换后把提升归因于某个模块。对照应使用相同模型和可比的 token／费用预算；报告实际开销与准确率的关系。

建议统计：真实根因在各阶段的召回、候选集合大小、概率可靠性、检索到有效原文的比例、步骤准确率、责任角色准确率、调用数、输入输出 token 及费用。按完整轨迹分开发、校准和最终评估；已反复分析的 Mini 不宜再被称为未见测试集。

这些论文为方法选择提供了依据，但对 JEV-RCTA 的收益仍是待验证假设。本次研究没有新增 API 消耗。
